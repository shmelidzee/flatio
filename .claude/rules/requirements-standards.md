# Requirements Standards — Flatio

Этот файл читают `product-analyst` и `product-manager`.
Здесь зафиксированы шаблоны и правила работы с требованиями.

---

## Шаблон ТЗ

Каждое ТЗ сохраняется в Notion после апрува владельца продукта.
Структура обязательна — не пропускать разделы, писать "N/A" если не применимо.

```
# [Название фичи или модуля]

## Версия
- Версия: v1.0
- Дата: YYYY-MM-DD
- Статус: Draft | Approved | Superseded

## Цель
Одно предложение: что именно решаем и для кого.

## Целевой рынок
- Текущий: Беларусь
- Планируемое расширение: [список рынков если известен]
- Архитектурные ограничения под расширение: [что нужно учесть]

## Пользователи
Кто использует эту фичу и как. Конкретные сценарии использования.

## Функциональные требования
Нумерованный список. Каждое требование:
- Атомарное: одно утверждение, одна проверяемая вещь
- Глагол в настоящем времени: "Система возвращает...", "Пользователь может..."
- Без слова "должен" — только факты о поведении

FR-1. ...
FR-2. ...

## Нефункциональные требования
NFR-1. Производительность: ...
NFR-2. Надёжность: ...
NFR-3. Безопасность: ...
NFR-4. Масштабируемость: ...

## Ограничения
Технические, юридические, бизнесовые ограничения которые влияют на реализацию.

## Интеграции
Какие внешние системы затрагивает: источники данных, Telegram API, и т.д.

## Открытые вопросы
Вопросы которые требуют решения владельца продукта перед началом разработки.
Формат: [Q] Вопрос → [A] Ответ (заполняется после обсуждения)

## История версий
| Версия | Дата | Изменения |
|--------|------|-----------|
| v1.0 | YYYY-MM-DD | Создан |
```

## Шаблон GitHub Issue

Каждый issue создаётся строго по этому шаблону.

```markdown
## Описание
Что нужно сделать. Одна задача, без перечисления подзадач.
Ссылка на раздел ТЗ: [FR-N из ТЗ vX.X]

## Acceptance Criteria
- [ ] Критерий 1 — конкретный, проверяемый, без двусмысленности
- [ ] Критерий 2
- [ ] Критерий 3

## Definition of Done
- [ ] Код написан и соответствует rules/dev-standards.md
- [ ] Тесты написаны и проходят (зелёный)
- [ ] Technical Reviewer поставил Approved
- [ ] Документация обновлена если изменился публичный интерфейс

## Контекст
Дополнительная информация: ссылки, решения, ограничения.
```

**Метки (labels) обязательны:**
- Тип: `feature`, `bug`, `chore`, `docs`
- Приоритет: `blocker`, `high`, `medium`, `low`
- Статус: `ready`, `in-progress`, `blocked`, `review`

**Milestone:** каждый issue привязан к milestone. Без milestone issue не берётся в работу.

---

## Правила атомарности задач

**Один issue = одна задача = максимум один день работы.**

Признаки что issue нужно разбить:
- В описании есть союз "и" между двумя независимыми действиями
- Acceptance criteria больше 5 пунктов
- Затрагивает больше одного слоя (например, и БД и API и UI)
- Название содержит слова "полностью", "весь", "все"

Признаки что issue слишком мелкий (объединить с другим):
- Выполняется за 30 минут
- Не имеет самостоятельной ценности без другого issue
- Acceptance criteria один пункт

---

## Правила приоритизации

`blocker` — без этого ничего не работает. Берётся первым.
`high` — core-функционал текущего milestone по роадмапу.
`medium` — улучшения и второстепенные фичи milestone.
`low` — nice-to-have, переносится если не успеваем.

Зависимости: если issue B зависит от issue A — проставить `blocked by #A` в описании B.
`product-manager` проставляет зависимости при создании, `software-engineer` пропускает `blocked` issues.

## Правила работы с противоречиями

Противоречие — когда два требования конфликтуют между собой или с существующей документацией.

**Алгоритм для `product-analyst`:**
1. Зафиксировать противоречие явно: "FR-3 конфликтует с FR-7 потому что..."
2. Предложить два варианта разрешения с trade-off каждого
3. Остановиться и сообщить владельцу продукта — не решать самостоятельно
4. Продолжить только после явного ответа

Противоречие не блокирует работу над несвязанными частями ТЗ.

---

## Правило мультирегиональности

Каждое архитектурное решение в ТЗ проверяется на вопрос:
**"Это решение будет работать для рынка X, отличного от Беларуси?"**

Если ответ "нет" или "не знаю" — добавить в раздел "Ограничения" и открытые вопросы.

Примеры что нужно проверять:
- Формат адресов и геолокации (разные страны — разные форматы)
- Источники данных (каждый рынок имеет свои площадки)
- Валюта и единицы измерения (м² vs ft², BYN vs UAH)
- Законодательные ограничения на парсинг и хранение данных

---

## Версионирование ТЗ

- Каждое обновление ТЗ после апрува — новая версия (v1.1, v1.2, v2.0)
- Черновики до апрува хранятся в `docs/drafts/` — не в Notion
- После апрува `product-analyst` уведомляет `product-manager` на сверку issues
- Устаревшие версии ТЗ в Notion помечаются статусом `Superseded`, не удаляются
