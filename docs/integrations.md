# Интеграции

Описание поведения внешних систем, с которыми взаимодействует Flatio, не покрытого стандартным
контрактом коннектора. Технические детали самих коннекторов (маппинг полей, пагинация,
дедупликация) — в `docs/parsers.md`.

## Kufar — фото через `rms.kufar.by` (issue #497)

### Симптом

Часть карточек объявлений с источником Kufar в Telegram-боте отправляется с плейсхолдером
вместо реального фото. В логе `PhotoProxyClient` зафиксирован случай, когда тело ответа на
запрос к `rms.kufar.by` — не байты изображения, а HTML-страница (`<html>\r\n<head...`), при этом
сам HTTP-запрос завершается успешно (200 OK).

### Что установлено

- Ошибка не воспроизводится как сетевой сбой — соединение и сам HTTP-запрос отрабатывают штатно,
  меняется только содержимое тела ответа.
- До этого исправления `PhotoDownloadConfig` использовал общий `RestClient` без `User-Agent` и
  `Referer` для всех источников фото (Onliner, Realt, Kufar) — Java-клиент по умолчанию посылает
  нехарактерный для браузера `User-Agent`, что типично триггерит анти-бот/гео-фильтры на CDN.
- Из окружения, где выполнялась эта задача, все поддомены `kufar.by` (включая `rms.kufar.by`)
  оказались недоступны на уровне TCP-соединения (timeout), при этом произвольные внешние хосты
  доступны — то есть эмпирическая проверка гипотезы против живого `rms.kufar.by` из этого
  окружения невозможна; вывод сделан по аналогии с уже рабочей конфигурацией `KufarClientConfig`
  (та же связка `User-Agent` + `Referer` уже используется для `api.kufar.by` и `re.kufar.by` и
  не вызывает проблем).

### Что было сделано (issue #497, не решило проблему)

- `PhotoProxyClient` при обращении к сконфигурированному хосту Kufar CDN добавлял к запросу
  browser-like `User-Agent` и `Referer` (та же строка `User-Agent`, что уже используется в
  `KufarClientConfig` для остальных запросов к Kufar).
- Тело ответа дополнительно проверялось на HTML-сигнатуру (`<html`, `<!doctype html`)
  независимо от источника — при обнаружении HTML скачивание трактовалось как неудачное, бот
  показывал плейсхолдер вместо битой картинки.
- **Результат (issue #511):** прод-лог того же дня после мержа показал тот же паттерн для каждого
  проверенного фото Kufar (7 из 7 попыток в приложенном PO окне) — заголовки гипотезу не
  подтвердили. Похоже на анти-бот/гео-гейт, не реагирующий на простую подмену `User-Agent`/`Referer`.

### Текущее решение (issue #515) — прямой URL вместо скачивания

Для фото с хоста `rms.kufar.by` `PhotoProxyClient.download()` (и его headers-логика выше) больше
не вызывается вообще. `SearchResultSender`/`FavoritesCallbackHandler` проверяют
`PhotoProxyClient#isKufarCdnUrl(url)` и, если true, передают URL в Telegram напрямую
(`InputFile(photoUrl)`), минуя скачивание байт нашим сервером.

**Осознанный риск при этом решении:** архитектура «скачать байты → загрузить в Telegram»
(см. Javadoc `PhotoProxyClient`) изначально была выбрана ради обхода **другой** проблемы —
некоторые CDN блокируют серверы Telegram по IP при прямой передаче URL (issue #364, пример —
`content.onliner.by` → `[400] failed to get HTTP URL content`). Прямая передача URL для Kufar
рисковала воспроизвести именно эту проблему. Эмпирическую проверку на проде провести не удалось
(нет доступа к prod из среды разработки), поэтому в код добавлен fallback: если Telegram отклоняет
прямую ссылку, карточка откатывается на плейсхолдер (не на `PhotoProxyClient.download()` — тот
гарантированно упрётся в тот же анти-бот-гейт). Если после этого решения фото Kufar продолжат не
показываться (или начнут падать в плейсхолдер массово из-за отказа Telegram принимать прямую
ссылку) — это будет сигналом, что issue #364 воспроизводится и для `rms.kufar.by` тоже, и вопрос
нужно поднимать заново.
