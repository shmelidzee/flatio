# Интеграции

Описание поведения внешних систем, с которыми взаимодействует Flatio, не покрытого стандартным
контрактом коннектора. Технические детали самих коннекторов (маппинг полей, пагинация,
дедупликация) — в `docs/parsers.md`.

---

## Kufar — фото через `rms.kufar.by` (issue #497)

### Симптом

Часть карточек объявлений с источником Kufar в Telegram-боте отправляется с плейсхолдером
вместо реального фото. В логе `PhotoProxyClient` зафиксирован случай, когда тело ответа на
запрос к `rms.kufar.by` — не байты изображения, а HTML-страница (`<html>\r\n<head...`), при этом
сам HTTP-запрос завершается успешно (200 OK).

### Что установлено

- Ошибка не воспроизводится как сетевой сбой — соединение и сам HTTP-запрос отрабатывают штатно,
  меняется только содержимое тела ответа.
- До этого исправления `PhotoDownloadConfig` использовал общий `RestClient` без `User-Agent` и
  `Referer` для всех источников фото (Onliner, Realt, Kufar) — Java-клиент по умолчанию посылает
  нехарактерный для браузера `User-Agent`, что типично триггерит анти-бот/гео-фильтры на CDN.
- Из окружения, где выполнялась эта задача, все поддомены `kufar.by` (включая `rms.kufar.by`)
  оказались недоступны на уровне TCP-соединения (timeout), при этом произвольные внешние хосты
  доступны — то есть эмпирическая проверка гипотезы против живого `rms.kufar.by` из этого
  окружения невозможна; вывод сделан по аналогии с уже рабочей конфигурацией `KufarClientConfig`
  (та же связка `User-Agent` + `Referer` уже используется для `api.kufar.by` и `re.kufar.by` и
  не вызывает проблем).

### Что сделано

- `PhotoProxyClient` при обращении к сконфигурированному хосту Kufar CDN
  (`photo-download.kufar-cdn-host`, по умолчанию `rms.kufar.by`) добавляет к запросу
  browser-like `User-Agent` и `Referer` (`photo-download.kufar-user-agent` /
  `photo-download.kufar-referer` — та же строка `User-Agent`, что уже используется в
  `KufarClientConfig` для остальных запросов к Kufar).
- Тело ответа дополнительно проверяется на HTML-сигнатуру (`<html`, `<!doctype html`)
  независимо от источника — если CDN всё же вернул HTML вместо изображения, скачивание
  трактуется как неудачное и бот показывает плейсхолдер, а не битую картинку.
- **Retry с backoff для этого случая сознательно не добавлен**: если ответ — гео-блокировка или
  анти-бот-гейт на стороне Kufar, повторный запрос в рамках того же короткого таймаута
  (`PhotoDownloadConfig`, 5 секунд) с высокой вероятностью упрётся в тот же результат, но удвоит
  задержку ответа бота пользователю. Если после этого исправления проблема продолжит
  воспроизводиться на проде — это будет сигналом, что причина не в заголовках, и стоит вернуться
  к вопросу отдельным issue.

### Ожидаемое поведение, если проблема не решена полностью

Если `rms.kufar.by` всё же продолжит возвращать HTML для части запросов (гео-блокировка на
стороне Kufar, не решаемая на нашей стороне) — плейсхолдер-фоллбек является ожидаемым поведением,
а не багом: архитектура «скачать байты → загрузить в Telegram» (см. Javadoc `PhotoProxyClient`)
сознательно не заменяется на прямую передачу URL Telegram — это воспроизведёт уже решённую
проблему блокировки серверов Telegram некоторыми CDN по IP (issue #364, пример — `content.onliner.by`).
